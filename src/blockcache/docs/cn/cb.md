## 方法学

- **工具**：`build/bin/blockcache/cb`（`src/blockcache/tools/benchmark/`），直接驱动客户端 `BlockCacheImpl`，不经 FUSE/VFS。时延从 `AsyncGet` 提交前到完成回调返回，纳秒计时进 log-linear 直方图（每 octave 256 桶，分位数误差 ≤0.4%），每 3s 打一行 `op/s MiB/s avg p50 p99 p999 max errors rejects little`，退出打印 `hits/misses/cpu_copied_bytes`。失败 op 只计 `errors`，不进 op/s 与时延；`little = IOPS×avg/(threads×iodepth)`，≈1 说明测出的时延与吞吐自洽。
- **键空间**：`chunkid = idx×blocks + 1`，每 16 块换 chunk，只由 (线程 idx, blocks, fsid, blksize) 决定。get 的 `--threads ≤ 灌数的 16` 即全命中；`--cache_store=none`（客户端无本地盘）、`--retrieve_storage=false`（miss 报错不回源），所以每格 `misses=0 errors=0` 是"纯远端命中"的硬证据。
- **路由**：客户端 shard 与节点 shard 都按 `Mix64(chunk id)` 选（两端 `--shards=8` 相同，无转发跳）；节点内按 chunk id 一致性哈希选盘，同 chunk 的 16 块落同一盘；节点按 `Hash(handle)`（含 block index）选，同 chunk 的块在两节点间交替。因此**单提交线程任意时刻只压 1 个客户端 shard、每节点 1 块盘**，扩展性以线程数扫描为主线。
- **口径**：每格 `--time_based --runtime=30`，3 轮交错随机序；每轮丢弃首个 3s 区间（含懒拨号）和末尾不足区间后取各区间中位数，再取 3 轮中位数；表中 `(min-max)` 为 3 轮 op/s 极差。同时采样两节点 `iostat -x 1`（四盘 r/s、rMB/s、util）、客户端 `port_rcv_data` 每秒差分（NIC 入向 GiB/s）、`mpstat -P 40-63`（shard 核占用）。
- **两套客户端配置**：默认 `--poll_mode=false --idle_poll_us=200 --offload_cpu_spin_us=0`；调优 `--poll_mode=true --offload_cpu_spin_us=1000`。节点默认 `poll_mode=false --buffer_pool_mb=256`，最后一节单独测节点 poll。
- **软件税** = e2e p50 − 当日盘 p50 − 当日 RDMA（4K：WRITE 4K + 2×SEND 128B；4M：WRITE 4M + 2×SEND 128B）。
- **公共参数**：
```bash
numactl --membind=1 --physcpubind=40-63 cb \
  --mds_addrs=10.220.88.31:6900 --fsid=10000 --cache_group=group-1 --cache_store=none \
  --remote_rdma=true --remote_rdma_device=mlx5_0 --rdma_port_num=1 \
  --shards=8 --pin_cpu=true --cpuset=40-47 --rdma_max_connections=8 \
  --op=get --retrieve_storage=false --time_based --runtime=30
# 4M: --blksize=4194304 --length=4194304 --blocks=512
# 4K: --blksize=4096 --length=4096 --blocks=100000
```

### 真实块文件与参考文件不同：SSD 对新写入数据的读时延随时间漂移

上面的参考文件数据**不能直接当 4M 块文件的地板**。用 fio 直接读 cb 实际读的那批 4M 块文件（`blocks/0/0/*_4194304`，
硬链接到临时目录后 `--opendir`），同一块盘、同一时段与 cb 交替测：

| 时刻 | fio 读 4M 块文件 p50/avg (µs) | 参考文件 4M p50 | 说明 |
| :--- | :--- | :--- | :--- |
| 20:22（写后 5 分钟） | ≈947（由 cb e2e 1142.8 − 175 − 20 反推） | — | 与参考文件一致 |
| 21:00 | 946–979 / 950–981 | 946 | 开始分化 |
| 21:27 | 979–1020 / 1007–1045 | — | 每连跑 15s 再涨 ~10µs |
| 21:52 | 1106–1139 / 1121–1159 | 970.8 | 与 cb 交替，见 §软件税 |

- 4M 块文件的读时延在 90 分钟里从 ~950 涨到 ~1130µs，而同盘的 20G 参考文件只从 946 涨到 971；节点重启、空闲 5 分钟、
  换 fio 引擎（libaio / io_uring / io_uring+fixedbufs / 关 THP）都不改变这一趋势，说明是盘内对新写入数据的后台迁移
  （SLC→TLC 之类），不是软件。
- 4K 块文件恰好相反：写后 2 小时仍 p50≈17–19µs（比介质随机读 70µs 快得多，数据在盘内缓冲），但 p90≈150µs，
  avg≈48µs——所以 4K 的器件地板取**压测同时段块层追踪/iostat 的 avg**（≈48µs），不取参考文件的 70µs。
- 结论：4M 的软件税只能用"同一时段、同一批文件、fio 与 cb 交替"的方法算；跨时段比较 4M e2e 绝对值没有意义
  （本报告 4M 各表的 e2e 会随测试进行缓慢上涨，读表时以同轮内相对关系为准）。

节点 shard 核都远未饱和，NIC 在 16 线程时已到线速的 89%。

## 软件税账目

方法：矩阵跑完后（01:18，节点 poll + 链式读，客户端调优），fio 与 cb 在同一块盘、同一批文件上交替各跑 3–4 次 10s
（4M：`blocks/0/0/*_4194304` 硬链接目录顺序读；4K：`blocks/0/800` 随机读），取相邻 fio 的均值作器件地板：

| | 器件 fio avg / p50 | cb e2e avg / p50 | RDMA 固有 | 软件税 avg / p50 |
| :--- | :--- | :--- | :--- | :--- |
| 4M QD1 | 1211.5 / 1187.8 | 1398.3 / 1376.3 | 172.7 + 2×1.24 = 175.2 | **11.6 / 13.3** |
| 4K QD1 | 48.0 / 19.5 | 65.2 / 31.9 | 2.4 + 2×1.24 = 4.9 | **12.3 / 7.5** |

（4K p50 与 avg 的软件税不同是因为器件分布双峰：p50 落在"盘内缓冲命中"的 19µs 一族，avg 才代表真实混合。）

这 ~12µs 的构成（按代码路径与 C1 数据估算）：客户端提交（inbox 投递 + shard 拾取 + protobuf 编码 + rkey 查找 + post_send）
≈2µs；节点收包/解析/索引查找/路径拼接 ≈2µs；链式 openat/read/close 一次提交与完成 ≈2µs；RDMA WRITE 完成后再发应答
（等 WRITE 的 CQE + 编码 + post）≈2µs；客户端完成路径（CQ 轮询 + 槽位解析 + 交给 CpuWorker + 回调）≈2µs；
cb 自身计时/回调 ≈1µs。判定阈值 25µs（≈2%）全部通过；默认口径（客户端不 poll、CpuWorker 停车）4K 再多 ~4µs、4M 再多 ~17µs。

硬证据（全部矩阵格）：cb 退出 misses=0、errors=0、rejects=0、`cpu_copied_bytes=0`（端到端零拷贝）；客户端日志无
`forwards it one hop`；节点日志只有 cb 进程退出后 5 分钟的 `Fail to keep rdma connection alive`（空闲会话回收，预期），
无 `buffer pool exhausted`。

## 优化：节点链式 open/read/close（commit `51f019c40`）

节点每次块读原来是三次串行 io_uring 往返（openat → read_fixed → close），每次一个 `io_uring_enter`、一趟 reactor、
一次协程恢复，外加每次 open/close 的进程 fd 表争用。`FileSystem::Read` 改为一次链式提交：
`openat_direct`（LINK）→ `read_fixed`（FIXED_FILE | HARDLINK，read 失败也保证 close 执行）→ `close_direct`，
fixed-file slot 复用不再有系统调用；内核缺 `IORING_FEAT_LINKED_FILE` 或 slot 用尽时回退旧路径。
（内核细节：direct-slot 的 open 不允许 `O_CLOEXEC`，否则 EINVAL。）单测 `test_blockcache_fs` 覆盖往返、短读、
不存在、slot 回收；功能冒烟用 `/mnt/dingofs` 挂载点 fio crc32c 写→drop_caches→verify_only 冷读通过。

## 两端 16 shard 的 4K 上限（2026-09-03 追加）

节点 `node.conf.s16`（= node.conf + `--poll_mode=true --buffer_pool_mb=512 --shards=16 --rdma_max_inflight_rpcs=256`，shard 钉 32-47），
客户端 `--shards=16 --cpuset=40-55 --rdma_max_inflight_rpcs=256 --queue_depth=16384`，进程圈在 40-63,96-127（其余线程用 node1 超线程）。
cb 先修了一处 harness 瓶颈（commit `30ed90027`：完成回调原来每次分配 std::function 投给单线程 execution_queue，250 万 op/s 以上该线程
99% CPU、区间数据错乱；改为每 worker 锁内直方图、reporter 定时合并）。

| 格 | 8 shard（tag o3） | 16 shard（tag s16b） | 变化 |
| :--- | :--- | :--- | :--- |
| 16×32 | 1666002 | 2271200 | +36% |
| 16×64 | 1999897 | 2815420 | +41% |
| 16×128 | 2228370 | **3136091（12250 MiB/s）** | +41% |
| 16×256 | 2282078 | 3118614 | 平台 |
| 16×512 | — | 3113060 | 平台（`queue_depth` 需 ≥8192，否则 rejects） |

313 万 op/s 处的瓶颈证据：
- 四盘 r/s = 832k / 708k / 686k / 794k，最忙的 0001 nvme3n1 `r_await` 2.2ms（其余 0.2ms）——**先饱和的是那块盘**。
  四盘负载差 ±10% 与灌数时的文件数（441k / 375k / 363k / 421k）完全成比例：一致性哈希每盘只有 160 个虚拟点
  （`ConsistentHash::kPointsPerWeight`），两盘分摊时粒度误差就是 ±8–10%。加大虚拟点数可把不均压到 ±2%，但会改变
  已有数据的落盘位置（升级后等同于清缓存），未改。
- 用 fio 直接读该盘上这批真实 4K 块文件（2.8 万文件子集）：8×QD64 = 818k、16×QD64 = 785k、32×QD32 = 606k（打过头反降）。
  **对这批离散小文件，单盘上限约 82 万 IOPS**，而 fio.md 的 100 万是 20G 单个大文件上测的；四盘上限 ≈ 4×82 万 = 328 万，
  313 万已达 95%，剩下 5% 是哈希不均。
- 两端 CPU 都还有余量：节点 shard 空转约 13–15%（perf：reactor 循环 7.7% + 各 poller），客户端 shard 空转约 30%。
  节点最大的单项仍是按路径 open 的 VFS 开销（`generic_permission` 3.9% + `__d_lookup_rcu` 3.1% + `__alloc_file` 1.7% …≈12%）。

结论：两端 16 shard 把 4K 上限从 223 万提到 313 万（+41%）；再往上受这批数据在盘上的物理上限（~82 万/盘）与放置不均限制，
不是软件；要接近 "4×100 万" 需要盘上数据像大文件那样连续放置（或更多盘）。测完节点已恢复 8 shard 原配置。

## 结论

1. **软件损耗**：远端命中路径的软件税 4K ≈ 12µs（avg 口径；p50 口径 7.5µs）、4M ≈ 12µs（0.9%），其余全部是硬件
   （NVMe 读 + RDMA 一次 SEND、一次 WRITE、一次 SEND）。端到端零拷贝（`cpu_copied_bytes=0`）、零 miss、零错误。
2. **扩展性**：4K 线程扩展完全线性且时延平坦；4M 聚合打满网卡线速（23551 vs 23550 MiB/s）；4K 大并发 222.8 万 op/s
   受四盘与节点 8 shard CPU 共同限制；4M 线程扩展的次线性来自四块盘上的排队（器件时延同步上涨），不是软件。
3. **默认配置的代价**：客户端默认（不 poll、CpuWorker 停车）在 4K 多 ~4µs、4M 多 ~17µs；节点 poll 与否对 4K 只差 1µs。
   已把 `offload_cpu_spin_us` 默认从 0 改为 200µs（与 `idle_poll_us` 对齐）拿回 4K 的 4µs；`idle_poll_us` 保持 200
   （4M 只赚 1%，轻载空转代价不值）。
4. **测试方法学教训**：这批 NVMe 对新写入数据的读时延在写后 1–2 小时内持续上涨（4M 块文件 950→1200µs），参考文件不受
   影响；任何"盘地板"都必须与被测对象同一时段、同一批文件交替测量，否则会把盘的漂移当成软件回归。

## 后续项

- 节点按路径 open 的 VFS 开销（~13% CPU）：open_by_handle_at 或常驻 fd 表可再提升 4K 大并发上限。
- 节点应答与数据同 QP 链式提交（WRITE 无信号 + SEND 有信号）或 WRITE_WITH_IMM，可再省 2–3µs（改协议，两端联动）。
- 客户端有在飞 RPC 时不睡眠（与 IoRing 的 PurePoll 同策略）可去掉 4M 默认口径的 ~13µs 睡眠税，代价是等待期占核，需产品决策。
- cb：多提交线程或批量提交，突破单线程 ~74 万 op/s 的 harness 上限；补 `--verify` 数据校验。
- 历史对照（cb.md 旧记录）：16×64 4K 读 152.7 万 op/s / 5963 MB/s → 本次同格 200.0 万 op/s / 7812 MiB/s。
