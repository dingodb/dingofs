# Running xfstests against DingoFS

[中文版](README_CN.md)

Adapters for running [xfstests](https://git.kernel.org/pub/scm/fs/xfs/xfstests-dev.git/)
against DingoFS. No modification to xfstests itself is required.

## How it works

```
sudo ./check generic/001
   │  reads <xfstests-tree>/local.config (FSTYP=fuse, FUSE_SUBTYP=.dingofs,
   │  TEST_DIR/SCRATCH_MNT — generated by setup.sh)
   ▼
mount -t fuse.dingofs xftest <root>/test
   │  mount(8) resolves the type to the helper /sbin/mount.fuse.dingofs
   ▼
mount.fuse.dingofs
   │  1. uses the device string as fsname and mount source (xftest)
   │  2. reads /etc/dingofs-xfstests.conf, resolves the meta-url for fsname
   │  3. launches: dingo-client <meta-url> <mountpoint> --fuse_subtype= ...
   │  4. polls until the mountpoint is live, then returns
   ▼
xfstests runs its test IO inside the mount
```

xfstests uses a two-device model, so there are **two independent DingoFS
instances**: `xftest` (TEST device — stays mounted, data accumulates across
tests) and `xfscratch` (SCRATCH device — "formatted" and remounted per test).
xfstests' native `FSTYP=fuse` support makes this workable without mkfs:
`_mkfs_dev` is a no-op, `_scratch_mkfs` mounts scratch and deletes all files,
and fsck/consistency checks are skipped.

## Files

| File | Purpose |
|---|---|
| `mount.fuse.dingofs` | mount helper (installed to `/sbin`): meta-url resolution, remount handling, mount-readiness wait, previous-instance wait between mount cycles |
| `setup.sh` | one-shot installer; also generates `local.config` into the xfstests tree and `/etc/dingofs-xfstests.conf` |
| `reset.sh` | unmounts both instances, waits for their clients to exit, then removes `<root>/runtime/{xftest,xfscratch}`; this resets filesystem contents only in local mode |

## Setup

```bash
# 1. Build xfstests once (Debian/Ubuntu deps shown)
sudo apt install -y xfslibs-dev libacl1-dev libgdbm-dev
git clone https://git.kernel.org/pub/scm/fs/xfs/xfstests-dev.git
cd xfstests-dev && make -j8

# 2. Build dingo-client (this repo)

# 3. Install the adapters
bash setup.sh <path-to-xfstests-tree> [root-dir]
```

`setup.sh` produces everything the flow needs:

| Artifact | Path | Consumed by |
|---|---|---|
| mount helper (copy of `mount.fuse.dingofs`) | `/sbin/mount.fuse.dingofs` | mount(8) on every `mount -t fuse.dingofs` |
| helper config (generated) | `/etc/dingofs-xfstests.conf` | the helper, re-read on every mount |
| xfstests config (generated) | `<xfstests-tree>/local.config` | `./check`, read on every run |
| directory layout | `<root>/{test,scratch,runtime}` | mountpoints + runtime data |
| `fsgqa` group and `fsgqa` / `fsgqa2` / `123456-fsgqa` users | system accounts | permission-related tests |

Everything lives under one root directory (default `/mnt/dingofs-xfstests`):

```
<root>/test      TEST_DIR mountpoint
<root>/scratch   SCRATCH_MNT mountpoint
<root>/runtime   per-fs runtime data (leveldb meta / storage / cache / logs)
```

Optional environment variables:

| Variable | Meaning | Default |
|---|---|---|
| `DINGOFS_CLIENT_BIN` | dingo-client binary | `<repo>/build/bin/dingo-client` |
| `DINGOFS_META_URL_TEMPLATE` | meta-url template, `{fsname}` substituted | empty = local file backend under `<root>/runtime` |
| `DINGOFS_EXTRA_FLAGS` | extra client flags, space-separated | empty |

Re-running `setup.sh` regenerates both config files (manual edits are
overwritten). After a client rebuild nothing needs reinstalling — the config
points at the binary path.

## Running

```bash
cd <xfstests-tree>
sudo ./check generic/001              # single test
sudo ./check generic/013 generic/070  # a specific list
sudo ./check -g quick                 # quick group
sudo ./check -g quick -e generic/062  # exclude known failures
```

On failure, evidence lives in two places:

- `<xfstests-tree>/results/generic/NNN.out.bad` (+ `.full`) — test-side diff/log
- `<root>/runtime/<fsname>/run/client.out` — output before daemonization
- `<root>/runtime/<fsname>/log/<pid>.stdout` and the glog files in the same
  directory — output from the background client; if test output contains
  `Transport endpoint is not connected`, look here for the crash stack

In **local mode**, use `bash reset.sh` to reset both filesystems to a blank
state. It unmounts both mountpoints, waits for this setup's dingo-client
processes to exit, then removes `<root>/runtime/xftest` and
`<root>/runtime/xfscratch` (deleting data while a client is running would corrupt
its leveldb/storage state). Typical occasions are switching backends, cleaning
a dirty TEST filesystem after failed tests, or starting a clean re-run.
Routine runs do not need it. Afterwards, run `./check` directly; the local
filesystems are re-created on first mount.

In **MDS mode**, `reset.sh` only unmounts the clients and removes their local
runtime data. It does **not** delete filesystem contents stored in MDS or the
remote storage backend; reset those filesystems through the corresponding
cluster administration workflow when a truly blank state is required.

## On-disk layout at runtime

With both instances mounted, everything lives under the root:

```
/mnt/dingofs-xfstests/
├── test/        FUSE mountpoint (source=xftest, type=fuse) — virtual view, empty when unmounted
├── scratch/     FUSE mountpoint (source=xfscratch)         — same
└── runtime/
    ├── xftest/                            TEST instance (xfscratch/ is identical, fully isolated)
    │   ├── meta/xftest/                   local-mode leveldb metadata: dir tree, inodes
    │   │   └── *.ldb *.log CURRENT MANIFEST-* LOCK   ← LOCK is what the previous-instance wait guards
    │   ├── storage/xftest/blocks/...      local file-backend data blocks, named <blockid>_<offset>_<len>
    │   ├── cache/<uuid>/                  read/write cache of this mount instance
    │   ├── log/
    │   │   ├── <pid>.stdout               daemonized client output — crash stacks land here
    │   │   ├── access_<pid>_<date>.log    FUSE access log
    │   │   └── dingo-client.{info,error,fatal}.log.*   glog
    │   └── run/
    │       ├── client.out                 startup output before daemonization
    │       └── fd_comm_socket.<pid>       hot-upgrade fd handover socket
    └── xfscratch/
```

Process view: one dingo-client per instance
(`local://xftest` on port 11945, `local://xfscratch` on port 11942).

In MDS mode `meta/` and `storage/` are unused (metadata lives in the MDS
cluster, data in the object store); `runtime/` then only carries cache, logs
and the run dir.

## Backend selection (meta-url)

The helper resolves a meta-url per fsname on every mount, first match wins
(all keys live in `/etc/dingofs-xfstests.conf`, re-read on every mount):

1. `META_URL_<fsname>` — per-fs override, e.g.
   `META_URL_xftest='local://xftest?storage=s3&ak=...&endpoint=...'`
2. `META_URL_TEMPLATE` — `{fsname}` substituted, e.g.
   `META_URL_TEMPLATE='mds://10.232.10.7:7400/{fsname}'`
3. built-in default — `local://{fsname}?storage=file&path=<root>/runtime/{fsname}/storage`

**Local mode (default)**: zero external dependencies; the filesystems are
auto-created on first mount.

**MDS mode**: the MDS/storage cluster must be up, and **both filesystems must
be created beforehand** (the client does not auto-create filesystems in MDS
mode):

```bash
dingo-cli fs create xftest    ...
dingo-cli fs create xfscratch ...
```

### `/etc/dingofs-xfstests.conf` reference

Written by `setup.sh` (all values shell-escaped), sourced by the helper on
every mount — edits take effect on the next mount, no reinstall needed:

| Key | Meaning |
|---|---|
| `CLIENT_BIN` | dingo-client binary the helper launches |
| `BASE_ROOT` | per-fs runtime data root (`<root>/runtime`) |
| `META_URL_TEMPLATE` | meta-url template, `{fsname}` substituted (resolution level 2) |
| `META_URL_<fsname>` | per-fs meta-url override (resolution level 1); add manually |
| `EXTRA_FLAGS` | extra dingo-client flags appended to the command line, **space-separated** (word-split on purpose, values containing spaces are not supported), e.g. `EXTRA_FLAGS='--v=1 --vfs_access_logging=false'` |
| `PORT_<fsname>` | per-fs dummy-server port override (default: stable per-fsname hash in 11900–11989); the two instances must not share a port |

## Design notes

- **Device strings are simple filesystem names** (`xftest` and `xfscratch`):
  xfstests compares the reported mount source against
  `$TEST_DEV`/`$SCRATCH_DEV` and later unmounts scratch by device. Names
  bare names keep the source comparison and by-device unmount unambiguous.
  The helper makes the client report the device string as its mount source by
  appending `fsname=<device>` through the existing `--fuse_mount_options`
  flag: the client adds its hardcoded `fsname=DingoFS:<fs>` first and the
  flag's options after it, and libfuse resolves duplicate options
  last-one-wins. Meta-URLs travel through the config file because their `&`
  characters are unsafe in xfstests' unquoted shell expansions.
- **`--fuse_subtype=` (empty)**: the helper mounts without a fuse subtype so
  the kernel reports fstype `fuse`, matching `FSTYP=fuse`. With the default
  `subtype=dingofs` the type reads `fuse.dingofs` and xfstests' `_fs_type`
  check rejects it at startup. `FUSE_SUBTYP` only selects the mount helper
  name; it does not need to match the kernel-reported type. (libfuse's own
  xfstests adapter relies on the same fact: its passthrough examples mount
  without a subtype.)
- **Mount readiness**: `--daemonize=true` forks before the FUSE mount
  completes. The helper first waits for `findmnt` to report the expected
  source and type (`fuse`), then uses a `statfs` round-trip to verify that the
  background client is serving requests rather than leaving an `ENOTCONN`
  corpse mount. xfstests starts IO immediately after mount(8) returns.
- **Previous-instance wait**: umount(2) returns before the old client has
  fully exited (local mode holds a leveldb LOCK; any mode holds the
  dummy-server port), so the helper waits for the previous instance of the
  same fs to exit before starting a new one.
- **Config file instead of environment**: mount(8) may invoke the helper with
  a stripped environment, so `/etc/dingofs-xfstests.conf` is the only
  parameter channel; a missing conf is treated as a broken install and the
  helper fails loudly instead of falling back to guessed defaults.
- **Deterministic dummy-server ports**: each fsname hashes (cksum) to a stable
  port in 11900–11989 (`xftest`=11945, `xfscratch`=11942), so TEST and SCRATCH
  instances coexist and a remount reuses its port. The port serves the
  client's debug HTTP endpoint (`curl 127.0.0.1:<port>/flags/...`).
- Running as root auto-enables `allow_other`; `default_permissions` is on by
  default (permission tests rely on both).
